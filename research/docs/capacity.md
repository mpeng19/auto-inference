# Capacity model

Generated by `scripts/capacity_report.py`. Do not edit by hand.

Every number here is a **ceiling**, not a forecast. Real serving lands well
under it — attention traffic, KV reads, imperfect overlap, and prefill
stealing decode steps all cost throughput. The useful output is the *ratio*:
hitting 60% of the roofline is a healthy server, 5% means something is wrong.

## Why two rooflines

Prefill and decode sit on opposite sides of the roofline:

- **Prefill is compute-bound.** A long prompt is one big matmul; the limit is FLOP/s.
- **Decode is memory-bound.** Each step reads weights to emit one token per
  sequence; the limit is HBM bandwidth.

For an MoE this second point is sharper than it first appears. Routing is
per-token, so at any real batch size the tokens in one step collectively
reach nearly *every* expert. `active_params` predicts FLOPs correctly and
under-predicts **bytes** badly.

    experts touched at batch  32: 112 / 128
    experts touched at batch  64: 126 / 128
    experts touched at batch 128: 128 / 128

So a decode step reads close to the whole model, not 10% of it.

Peak FLOPs is the **dense** figure. The commonly quoted ~1979 TFLOP/s
assumes 2:4 structured sparsity, which inference serving does not use.

### Validation against measurement

| | |
|---|---|
| roofline ceiling | 56.2 rps |
| **measured** max throughput | **34.3 rps** |
| achieved fraction | **61%** |
| measured SLO knee | 35.6–49.1 rps |
| theoretical decode step | 9.02 ms |
| **measured** p99 TPOT | 24.0 ms |

61% of the bandwidth roofline is a
healthy result for a real serving stack. The gap between the theoretical
9.0 ms decode step and the measured 24 ms TPOT
is the clearest single lead we have: it is roughly the cost of prefill
chunks interleaving into decode batches, which is exactly what a scheduler
change can move.

used one average request would hide both.
